# Вклад в QuizHub

## Перед началом

1. Прочитайте [ТЗ V1](docs/PRODUCT_SPECIFICATION_V1.md).
2. Проверьте [ROADMAP.md](ROADMAP.md) и [статус реализации](docs/IMPLEMENTATION_STATUS.md).
3. Убедитесь, что изменение относится к согласованному объёму V1. Новые функции за пределами V1 требуют отдельного Change Request.

## Рабочий процесс

- Создавайте отдельную ветку для самостоятельной задачи.
- Не коммитьте напрямую в `main`, если задача требует review или CI.
- Не смешивайте косметический рефакторинг, изменение игровой логики и миграцию данных в одном PR без необходимости.
- Сохраняйте существующие публичные интерфейсы модулей, пока все потребители не переведены.
- Не удаляйте файлы только по названию или возрасту: сначала проверьте импорты, workflow, тесты и ссылки в документации.

## Проверки перед PR

```bash
node --experimental-default-type=module scripts/validate-questions.mjs
node --experimental-default-type=module --test tests/*.test.mjs
npm install --prefix functions
npm run --prefix functions build
npm run --prefix functions check
```

Для изменений Firebase callable, Firestore store или правил дополнительно запускайте соответствующие Emulator tests. Не используйте Production project для интеграционных тестов.

## Требования к Pull Request

PR должен содержать:

- краткое описание проблемы и решения;
- Requirement ID или ссылку на раздел ТЗ;
- список изменённых областей;
- команды и результаты тестирования;
- ограничения, миграционные риски и rollback-план, если применимо;
- обновление ROADMAP / IMPLEMENTATION_STATUS, когда меняется фактический статус.

Зелёный UI preview не заменяет unit-, security- и emulator-проверки.

## Безопасность

- Не добавляйте секреты, приватные ключи, реальные токены и пользовательские данные.
- Не отключайте fail-closed проверки ради прохождения тестов.
- Не ослабляйте Firestore Rules без отдельного обоснования и аудита.
- Не запускайте backfill, миграции, Production deploy или массовые изменения данных без явного разрешения.
- Исторические клиентские записи не маркируйте как verified ledger events без проверки происхождения.

## Стиль кода и комментарии

- Используйте существующий стиль JavaScript ES Modules.
- Комментарии должны объяснять причину, инвариант или ограничение, а не пересказывать следующую строку кода.
- Удаляйте устаревшие TODO и комментарии только после проверки, что они действительно потеряли актуальность.
- Не оставляйте имена моделей, временные подсказки генератора и личные заметки в исходниках.
